YOLO ↔ Ergo Trustless Peg — Flow Diagram

How a user moves coins between YOLO (a dedicated-PoW Autolykos2 chain) and Ergo with no federation, no oracle, no trusted bridge operator. Both chains run ErgoScript 6.0, so each chain's contracts can independently verify the other chain's block headers and transactions.

Cast of characters

👤 Alice
The user. Wants to move funds between chains. Submits the lock and the mint/unlock transactions.
📡 Relayer
Anyone with a node. Pushes block headers from one chain into the relay contract on the other. Permissionless — no privilege.
⛏️ YOLO miners
Produce YOLO blocks via Autolykos2. They don't run the bridge — they just mine YOLO normally.
⛏️ Ergo miners
Produce Ergo blocks. Same role — mine normally, no bridge duty.
📜 Contracts on YOLO
Lock-USE box (holds locked Ergo assets), Mint-wYOLO box, ErgoRelay box (knows Ergo's chain), DoubleSpendPrevention.
📜 Contracts on Ergo
Lock-YOLO box (holds locked YOLO when wrapped), Mint-wUSE box, YoloRelay box (knows YOLO's chain), DoubleSpendPrevention.

Setup: two relays run in the background, forever

Before any user can bridge, both chains need a live header relay of the other chain. This is independent of users — it just keeps running.

YOLO Chain

ErgoRelay box
Stores AVL tree of Ergo headers it has verified. Updated by anyone submitting new Ergo headers + AVL insert proofs.
Verifier op used
ergoHeader.checkPow — Ergo's built-in. Fixed cost 700.
⇆
two independent relays

Ergo Chain

YoloRelay box
Stores AVL tree of YOLO headers it has verified. Updated by anyone submitting new YOLO headers + AVL insert proofs.
Verifier op used
Global.powHit(k, msg, nonce, h, N) — generalized Autolykos2 for custom params. Cost ~1000.
R
Relayer pushes a new header happens on both chains, always
A bot watches chain X for new blocks. When one arrives, the bot builds a tx that spends the relay box on chain Y, attaches the new header bytes, attaches AVL insertion proofs (computed off-chain), and submits.

Flow A: send YOLO from YOLO chain → Ergo (as wYOLO)

Story: Alice has 100 YOLO on the YOLO chain. She wants 100 wYOLO tokens on Ergo (so she can trade them on Ergo DEXes). She locks the YOLO on its native chain, proves the lock to Ergo, and Ergo mints wYOLO to her.
1
Alice locks 100 YOLO in a Lock box YOLO chain
Alice sends her 100 YOLO into a special contract box. The box says: "I hold 100 YOLO for Alice's Ergo address; I can only be unlocked by proof that the corresponding wYOLO was burned on Ergo, plus a waiting period."
Who submitsALICE Standard wallet transaction.
Box createdLock-YOLO box on YOLO chain. Registers store: amount, Alice's Ergo destination address, lock height.
Tx feeTiny YOLO fee.
2
A YOLO miner mines Alice's tx into block N YOLO chain
Normal mining. The miner doesn't know or care that this is a bridge tx. It's just another transaction in their mempool.
Who submitsYOLO MINER The block producer. No bridge-aware logic needed.
What happensAlice's Lock box is now in YOLO's UTXO set, at block height N.
⏳ Wait ~50 YOLO confirmations to prevent reorgs unwinding the lock
3
Relayers push YOLO headers N through N+50 into the YoloRelay on Ergo Ergo chain
This is happening in the background continuously anyway. By the time Alice has waited her confirmations, the YoloRelay on Ergo already knows about block N+50.
Who submitsRELAYER Anyone. Pays Ergo tx fee per header. Nothing privileged.
What Ergo verifies in-scriptGlobal.powHit(k, msg, nonce, h, N) recomputes the Autolykos2 hit for the YOLO header, compares to the YOLO target from nBits. AVL insert proofs validate the header is correctly chained.
Result on ErgoYoloRelay box's AVL tree now contains YOLO blocks up to N+50, including the merkle root of block N.
4
Alice submits the Mint-wYOLO transaction on Ergo Ergo chain
Alice's wallet builds a tx that says: "I want 100 wYOLO. Here is proof that my YOLO Lock box really exists in YOLO block N, here is the YoloRelay box as evidence that block N has 50+ confirmations on YOLO."
Who submitsALICE Or anyone helping her — the proof doesn't require her signature, just the merkle proof.
Inputs to the Mint contract on Ergo(a) Data input: YoloRelay box. (b) Context vars: Alice's YOLO Lock box bytes, merkle proof of its inclusion in YOLO block N, YOLO header id, header lookup AVL proof.
What the Mint contract checks(1) YoloRelay's best-chain AVL contains block N. (2) Block N has ≥50 confs (compare to YoloRelay's tip height). (3) Merkle path from the Lock-tx hash hashes up to block N's transactionsRoot. (4) The Lock box matches the expected Lock contract template. (5) DoubleSpendPrevention tree doesn't already contain this Lock box ID.
Result100 wYOLO tokens minted to Alice's Ergo address. Lock box ID added to DoubleSpendPrevention tree.
Key trust observation: No one was trusted at any step. The Mint contract on Ergo doesn't trust Alice (she could lie), doesn't trust the relayer (the relayer can only submit headers that pass PoW — they can't forge YOLO state), and doesn't trust any human. It only trusts its own ErgoScript verification of math.

Story: Alice has 100 USE (a stablecoin on Ergo) and wants to spend them on a dApp on YOLO. Mirror of Flow A — the chain roles just swap.

Alice locks 100 USE in a Lock-USE box on Ergo Ergo chain
Same idea, opposite chain. USE tokens go into a contract box that says "release only on proof of wUSE burn on YOLO."

Box createdLock-USE box on Ergo. Registers: USE amount, Alice's YOLO address, lock height.
2
An Ergo miner mines Alice's tx into Ergo block M Ergo chain
Same as before, just on Ergo. Standard mining.
⏳ Wait ~30 Ergo confirmations
3
Relayers push Ergo headers M through M+30 into the ErgoRelay on YOLO YOLO chain
Same background process, opposite direction. This is the easy direction because YOLO contracts can call ergoHeader.checkPow directly — a single fixed-cost op.

Result on YOLOErgoRelay box's AVL tree now contains Ergo blocks up to M+30, including the merkle root of block M.
4
Alice submits the Mint-wUSE transaction on YOLO YOLO chain
Same as Flow A step 4, with chains swapped. Alice (or anyone for her) proves to YOLO that the USE Lock box exists in Ergo block M, and YOLO mints her 100 wUSE.
Who submitsALICE Standard YOLO wallet tx.
What the YOLO Mint contract checksErgoRelay knows block M, ≥30 Ergo confs since M, merkle path proves Lock-USE tx is in block M's transactionsRoot, Lock box matches template, no double-mint.
Result100 wUSE tokens minted on YOLO to Alice's address.

Flow C: unwrap wYOLO on Ergo back to YOLO (the round trip)

Story: Alice has 100 wYOLO on Ergo and wants her original 100 YOLO back on the YOLO chain. Direction reverses: she burns on Ergo, proves the burn to YOLO, the YOLO Lock box releases.
1
Alice burns 100 wYOLO on Ergo Ergo chain
Alice spends her 100 wYOLO into a "Burn" contract box that destroys the tokens (or sends to a known-unspendable address) and records: "100 wYOLO burned, return to Alice's YOLO address X, burn height H."
Who submitsALICE
Box createdBurn-receipt box on Ergo. This is the analogue of the Lock box, but in reverse direction.
2
Ergo miners include the burn tx in block M' Ergo chain
⏳ Wait Ergo confirmations + relayer pushes headers M'..M'+30 to ErgoRelay on YOLO
3
Alice submits the Unlock-YOLO transaction on YOLO YOLO chain
Alice's wallet builds a tx that says: "Open the Lock-YOLO box from way back when. Here is proof that I burned the corresponding wYOLO on Ergo, and that the burn has enough confirmations."
InputsThe original Lock-YOLO box (still sitting on YOLO since Flow A), ErgoRelay box as data input, context vars with the Burn-receipt box bytes + merkle proof + header lookup proof.
What the Unlock contract checks(1) ErgoRelay knows Ergo block M'. (2) ≥30 Ergo confs. (3) Merkle path proves Burn-receipt tx is in block M'. (4) Burn amount matches Lock amount. (5) Burn destination address matches Alice. (6) DoubleSpendPrevention on YOLO doesn't already contain this Burn box ID.
ResultLock-YOLO box on YOLO opens. Alice gets her original 100 YOLO back. Round trip complete.

What makes this trustless (the ELI5 sentence)

  • The mint/unlock contracts do not trust the relayer. The relayer can only submit headers that pass PoW verification in-script — they can't forge a YOLO block any more than a real YOLO miner can without doing the work.
  • The mint/unlock contracts do not trust Alice. She must provide a real merkle proof against a real header that the relay has accepted. If she lies, the contract rejects the tx.
  • No human has a privileged key anywhere in this flow. The whole bridge runs on ErgoScript verifying math: PoW math, merkle math, AVL tree math.
  • The only "actor" with any real role is the relayer, and they are completely substitutable — anyone can take over the role at any time by just running the bot. There is no relayer set, no quorum, no governance.

What is NOT in this picture, and why:
Miners do not run any bridge logic. They produce blocks the way they always do. The bridge exists entirely as user-land contract logic on both chains.
No federation, multi-sig, or oracle. The verification surface is: (a) Autolykos2 PoW math via ErgoScript 6.0's Global.powHit and Header.checkPow; (b) merkle inclusion proofs against block headers; (c) AVL trees for header history and double-spend prevention.
The current ross-weir reference repo has the BTC→Ergo relay shipping (~3 test cases on real headers), plus the merged-mining sidechain lock/unlock contracts. For YOLO ↔ Ergo specifically, the BTC relay needs to be reworked to call Global.powHit instead of doubleSha256, and the lock/unlock contracts need to swap the merged-miner-signature gate (preHeader.minerPk) for the relay-data-input pattern shown above.
